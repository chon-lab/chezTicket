Regras de negócio implementadas

  • Defaults de criação: categoria nova recebe slug derivado do nome; evento novo sem classificação/política informada recebe LIVRE/PADRAO.
  • Unicidade: nome de categoria é único, no cadastro e na renomeação.
  • Edição bloqueada por status: evento CANCELADO/ENCERRADO não aceita PUT.
  • Publicar exige descrição preenchida (regra ligada ao UC-06 da modelagem).
  • Remoção de evento — só ADMIN quando publicado: em RASCUNHO qualquer um remove; em qualquer outro status, só administrador.
  • Remoção bloqueada por integridade referencial: remover uma categoria com evento vinculado (ou qualquer remoção que violaria uma chave estrangeira) retorna 409

Erros seguem RFC 7807 (application/problem+json): 400 payload malformado, 403 sem permissão, 404 inexistente, 409 conflito, 422 regra de negócio violada.

Modelo de dados e testes

Duas perguntas sustentam qualquer sistema em construção: onde os dados moram, e como saber que o que já foi feito continua funcionando à medida que o projeto cresce. Esta seção responde as duas — o banco implementado, e os testes automatizados que o protegem.

Modelo de dados

O banco precisa de uma estrutura fixa — tabelas, colunas, relações — para guardar organizador, evento, categoria e o resto. Essa estrutura também precisa evoluir de forma controlada, e não por alguém alterando o banco na mão. É isso que o Flyway garante: cada mudança de schema é um arquivo numerado, aplicado sozinho e na ordem certa toda vez que a aplicação sobe.

Hoje o schema tem 17 tabelas, derivadas do modelo lógico da modelagem UML (sem setor/lote/checkin, removidos do modelo depois da primeira versão): 

usuario, participante, organizador, administrador,
categoria, local, evento, sessao, tipo_ingresso, cupom,
reserva, pedido, item_pedido, pagamento, reembolso, ingresso, repasse_financeiro
Migrações
V1esquema inicial — as 17 tabelas
V2seed de 8 categorias iniciais
V3dados de demonstração: 2 organizadores, 1 administrador (usuario_id=3), 2 locais — testa o CRUD pelo Swagger sem cadastrar nada antes

Testes automatizados

Testar na mão — subir o Docker, chamar cada endpoint pelo Swagger — prova que algo funcionou uma vez, não que vai continuar funcionando depois da próxima mudança. Por isso cada regra importante virou um teste automatizado: um programa curto que exercita aquela regra sozinho e avisa, em segundos, se algo quebrar.

Foram realizados testes em três camadas, cada uma isolando uma preocupação diferente. Um exemplo real de cada:

CamadaIsolaExemplo real
Domínio
CategoriaTest, EventoTest		 a regra de negócio pura, sem Spring — roda em milissegundos naoDevePublicarSemDescricao()
Aplicação
CategoriaServiceTest, EventoServiceTest		 a orquestração do caso de uso, com Mockito simulando o banco administradorRemoveEventoPublicado()
Persistência
*PersistenceAdapterIT		 contra um MariaDB real em Docker (Testcontainers), Flyway rodando de verdade deveFiltrarPorStatusCategoriaEOrganizador()

mvn test roda as duas primeiras camadas (rápido, sem precisar de Docker); mvn verify — com o Failsafe agora configurado — roda tudo, *IT incluído: 

mvn test     # dominio + aplicacao — rapido, sem Docker
mvn verify   # tudo, incluindo os *IT — requer Docker
